## 设计原则

### 每个 Skill 必须包含

1. **能力边界**：能做什么 / 不能做什么  
2. **输入格式**  
3. **输出格式**  
4. **使用场景**  
5. **反 Slop 规则**

### 反 Slop 核心

- 输出须有具体数据，禁止空泛「分析完成」  
- 不确定须标明，禁止瞎猜  
- 越界须上报  
- 禁止废话式「分析」

## calendar.md（日程管理）

```markdown
# 日历技能

## 能力边界

### 能做
- 读取指定日期的日程安排
- 查找空闲时间段
- 计算日程冲突
- 列出下周/本月日程概览

### 不能做
- 不能修改日历（需要用户确认）
- 不能创建会议邀请
- 不能访问第三方日历应用（除非配置）

## 输入格式
```
命令：[查看/分析/查找]
日期：[YYYY-MM-DD] 或 [today/tomorrow/next week]
范围：[上午/下午/全天/具体时段]
```

## 输出格式
```
📅 [日期]日程

09:00-10:00 [会议名称] @[地点]
10:00-12:00 空闲
13:00-14:00 [会议名称] @[地点]
14:00-15:00 空闲

空闲时段：10:00-12:00, 14:00-15:00
```

## 使用场景
- 用户问"明天有什么安排"
- 用户问"这周哪天上午有空"
- 用户让安排会议，需要先查空闲时间

## 使用流程
1. 读取日历数据
2. 解析日程
3. 按格式输出
4. 如需分析空闲时间，计算后输出

## 反Slop规则
1. 必须输出具体时间，不能只说"明天有3个会议"
2. 不确定的时间（如外部邀请），说明"不确定"
3. 冲突必须明确指出，不能忽略
```

## todo.md（待办管理）

```markdown
# 待办技能

## 能力边界

### 能做
- 列出所有待办
- 按优先级排序
- 添加新待办
- 标记完成
- 分析待办完成率

### 不能做
- 不能自动拆解复杂任务（需要人工）
- 不能设置截止日期（需要用户确认）
- 不能提醒（未来扩展）

## 输入格式
```
命令：[列表/添加/完成/分析]
内容：[任务内容]（仅添加时需要）
优先级：[高/中/低]（仅添加时需要）
```

## 输出格式
```
📋 待办列表

🔴 高优先级
1. [任务] [截止：日期]
2. [任务]

🟡 中优先级
1. [任务]

🟢 低优先级
1. [任务]

共X项 | 完成率：X%
```

## 使用场景
- 用户问"我有什么待办"
- 用户说"帮我加一个待办"
- 用户说"标记XX完成了"
- 用户问"这周完成率怎么样"

## 反Slop规则
1. 完成的任务不能删除，只能标记
2. 必须问截止日期，不能自己瞎编
3. 完成率必须基于实际数据计算，不能说"大概80%"
```

## content.md（小红书内容创作）

```markdown
# 小红书内容创作技能

## 能力边界

### 能做
- 根据选题生成文案
- 根据content-rules.md的规范创作
- 生成多版本备选
- 根据反馈修改文案

### 不能做
- 不能代替用户发布
- 不能生成图片（需要其他工具）
- 不能预测爆款（只能参考规律）

## 输入格式
```
选题：[选题内容]
风格：[正式/轻松/干货/情感]
长度：[短/中/长]
版本：[v1/v2/v3]
```

## 输出格式
```
# [标题]

[正文，使用emoji，每段不超过3行]

#标签1 #标签2 #标签3

---
生成时间：[时间]
版本：[v1]
```

## 使用场景
- 选题确定后生成文案
- 用户说"帮我写一个XX的文案"
- 用户说"这个文案太长了，帮我缩短"

## 反Slop规则
1. 必须严格遵守content-rules.md的规范
2. 不能写虚假信息或夸大
3. 每个emoji必须有意义，不能堆砌
4. 标签不能超过10个
5. 禁止写"姐妹们"这种油腻开头
```

## code-review.md（代码 Review）

```markdown
# 代码Review技能

## 能力边界

### 能做
- 分析代码逻辑
- 发现潜在bug
- 提出改进建议
- 评估代码质量
- 生成Review评论

### 不能做
- 不能修改代码（只能建议）
- 不能保证找出所有问题
- 不能替代人工Review

## 输入格式
```
仓库：[GitLab项目ID或名称]
MR：[MR编号]
语言：[编程语言]
范围：[只看diff/完整代码]
```

## 输出格式
```
🔍 Code Review: [MR标题]

## 总体评价
[好/有问题/需要大改]

## 问题列表

### 🔴 必须修复
1. [文件:行号] [问题描述]
   建议：[修复方案]

### 🟡 建议改进
1. [文件:行号] [问题描述]
   建议：[改进方案]

### 🟢 做得好的
1. [具体位置] [为什么好]

---
Review完成时间：[时间]
```

## 使用场景
- 收到MR Review请求
- 用户说"帮我Review这个MR"

## 反Slop规则
1. 必须指出具体文件和行号，不能只说"这段代码有问题"
2. 问题必须说明原因，不能只说"这不对"
3. 不能过度Review，把代码风格问题当bug
4. 禁止" LGTM "式的敷衍Review
```

## prd-reshape.md（PRD 文档重塑）

```markdown
# PRD文档重塑技能

## 能力边界

### 能做
- 读取原始PRD（Markdown）
- 转换为AI友好的标准化格式
- 提取关键信息（背景、目标、方案）
- 生成结构化摘要

### 不能做
- 不能访问钉钉知识库（需扩展）
- 不能保证内容100%准确（需要人工审核）
- 不能替代产品经理决策

## 输入格式
```
文件路径：[PRD文件路径]
目标格式：[完整版/摘要版/技术版]
```

## 输出格式
```
# [功能名称]

## 一句话概述
[1-2句话说明这是什么]

## 背景
[为什么需要这个功能]
- [具体原因1]
- [具体原因2]

## 目标
- [可量化的目标1]
- [可量化的目标2]

## 用户故事
作为 [用户类型]
我希望 [功能]
以便 [收益]

## 技术方案
[AI友好的技术描述，避免模糊词汇]

## 验收标准
- [可验证的标准1]
- [可验证的标准2]

## 风险
- [已知风险]
- [缓解方案]

---
重塑完成时间：[时间]
原文件：[文件名]
```

## 使用场景
- 用户提供了原始PRD，需要AI分析
- 用户说"帮我把这个PRD重写成AI友好的格式"

## 反Slop规则
1. 不能省略原始文档中的任何关键信息
2. 技术方案必须具体，不能说"优化性能"这种废话
3. 验收标准必须可验证，不能说"用户体验好"
4. 发现原始文档有问题，必须指出
```

## gitlab.md（GitLab 集成）

```markdown
# GitLab集成技能

## 能力边界

### 能做
- 获取MR列表
- 获取MR详情和diff
- 提交MR评论
- 获取项目信息

### 不能做
- 不能merge MR
- 不能创建MR
- 不能访问私有仓库（除非配置凭证）

## 配置要求
每台机器必须在 `~/.gitlab-token` 文件中配置Private Token

## 输入格式
```
命令：[list-mrs/get-mr/review]
项目ID：[项目ID]
MR编号：[MR编号]（仅get-mr/review需要）
```

## 输出格式

### list-mrs
```
📋 [项目名] MR列表

#1 [标题] @[作者] [状态] [时间]
#2 [标题] @[作者] [状态] [时间]
```

### get-mr
```
🔍 MR #[编号]: [标题]

状态：[open/merged/closed]
作者：[作者]
审阅者：[审阅者列表]

变更：
+[新增行数] -[删除行数]

描述：
[MR描述]
```

## 使用场景
- Review Agent需要获取MR信息
- Consult Agent需要提交Review评论

## 反Slop规则
1. 不能访问未授权的仓库
2. 操作失败必须说具体原因
3. Token过期必须立即上报
```
